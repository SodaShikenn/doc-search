# 給与計算バッチ設計ノート（サンプル）

給与計算エンジンの設計方針をまとめたフィクションの設計ノート。実在の企業・データとは関係ない。各セクションは検索用に自己完結で書く。

## 計算パイプライン

給与計算は「勤怠確定 → 支給・控除計算 → 源泉徴収 → 振込データ生成」の4ステージのパイプラインとして実装する。勤怠確定ステージでは勤怠締めが完了した従業員のみを計算対象にスナップショットし、以降のステージは勤怠側の変更に影響されないようにする。支給・控除計算ステージで基本給・割増賃金・各種手当と社会保険料・住民税などを算出し、源泉徴収ステージがその課税支給額合計を入力として所得税を求める（ステージ間の依存が一方向になるよう、課税対象額はここで初めて確定させる）。最後の振込データ生成では差引支給額から全銀フォーマットの振込データと給与明細を作る。各ステージは従業員単位で独立に計算できるため、テナント内は従業員単位で並列化し、失敗した従業員だけを再実行できる粒度にする。

## 料率マスタの管理

健康保険・厚生年金・雇用保険の料率、源泉徴収税額表、標準報酬月額の等級表は、すべて「適用開始日付きのバージョン」を持つマスタとして管理する。レコードは (料率種別, 適用開始日, 値) の形で追加のみ行い、既存バージョンは更新・削除しない。計算時は「支給対象月の基準日 <= 適用開始日の最大のもの」を引く resolver を共通化し、個々の計算ロジックに日付比較を書かせない。毎年の改定（健康保険は3月分〜、雇用保険は4月分〜、税額表は1月〜と時期がバラバラ）に備えて、改定データは施行前に投入して予約できるようにし、投入漏れを検知するために「N日以内に適用開始日を迎えるバージョンが存在するか」の監視を入れる。過去月の再計算では当時の料率が引かれることをテストで保証する。

## 再計算と冪等性

締め後に発覚する遡及修正（打刻漏れ、手当の付け忘れ、扶養情報の遡り変更など）は避けられない前提で設計する。計算結果は上書きせず、計算実行ごとに calculation_run としてバージョン管理し、確定済みの月に対する修正は「再計算した正しい値 − 確定済みの値」の差額を翌月の調整項目として自動生成する方式を基本とする（締め解除して同月内で再確定するフローも管理者向けに残す)。バッチのリトライ安全のため、計算リクエストには (テナントID, 対象年月, run番号) から成る冪等キーを付け、同一キーの再実行は前回結果を返すだけにする。振込データ生成も同様に、同じ run から二重にファイルが出力されないよう出力済みフラグを run 側に持たせる。

## 端数処理

丸め規則は項目ごとに異なるため、計算ロジックにハードコードせず項目マスタの設定として持つ。設定は「丸め方式（切り捨て / 切り上げ / 四捨五入 / 五捨六入）× 丸め単位（1円 / 10円 / 100円）× 丸めタイミング（項目単位 / 合計後）」の組で表現する。たとえば社会保険料の被保険者負担分は五捨六入（50銭以下切り捨て・50銭超切り上げ）が原則だが、事業所によって円未満切り捨ての運用もあるため設定可能にしておく。計算の中間値は丸めずに保持し（内部は固定小数点、最小単位0.01銭）、丸めは各項目の最終出力時に一度だけ適用する。丸め順序が変わると合計が1円ずれて振込・仕訳の不一致になるため、丸め処理は共通の Rounding サービスに集約し、項目ごとの適用結果を計算ログに残す。

## 監査とマイナンバーの扱い

給与データは特に機微性が高いため、閲覧・計算実行・確定・振込データ出力のすべての操作を監査ログに記録する（誰が・いつ・どのテナントのどの run に対して・何をしたか）。マイナンバーは給与計算エンジン本体では扱わず、源泉徴収票などの帳票生成時にのみ専用の番号保管サービスから参照する。番号保管サービスは暗号化ストレージと独立したアクセス権限（RBACの専用ロール）を持ち、参照はすべて目的コード付きでログに残す。アプリケーションログ・エラーメッセージ・APM のトレースにはマイナンバーおよび口座番号を出力しない。構造化ログのシリアライザに機微フィールドのマスキングを組み込み、うっかり出力をコードレビュー任せにしない。ログの保持期間と削除（退職者データの保管期限）も要件として明文化する。
