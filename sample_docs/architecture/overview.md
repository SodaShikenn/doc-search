# システム構成概要（サンプル）

架空の会計SaaS「LedgerCloud」のアーキテクチャ概要。docsearch のデモ用サンプルドキュメント。

## 全体像

- フロントエンド: React + TypeScript の SPA。デザインシステムのコンポーネントを使用
- API: Ruby on Rails のモノリス + 一部ドメインをマイクロサービスとして切り出し
- 非同期処理: Sidekiq によるジョブキュー。帳票生成・一括インポート・仕訳の再集計を担当
- データベース: Aurora MySQL。テナントIDによる論理分離
- 全文検索: OpenSearch。取引先名・摘要のあいまい検索に使用
- インフラ: AWS (ECS Fargate)、IaC は Terraform

## リクエストの流れ

1. ブラウザ → CloudFront → ALB → Rails API
2. 認証はセッション + 一部APIはOAuth2のアクセストークン
3. Rails はテナントコンテキストをミドルウェアで解決し、以降のクエリに自動で tenant_id を付与
4. 重い処理はジョブinto Sidekiq、完了は WebSocket でクライアントに通知

## 仕訳データのライフサイクル

取引の入力（手入力・銀行明細の自動取込・API連携）→ 仕訳候補の推測（機械学習による勘定科目・税区分のサジェスト）→ ユーザー確認 → 仕訳確定 → 集計テーブル更新（非同期）→ 帳票（試算表・決算書）に反映。

集計テーブルは結果整合性を許容しており、確定から反映まで最大数分の遅延がある。

## 障害時の設計

- リードレプリカへのフェイルオーバーは自動。書き込み系は数十秒のダウンタイムを許容
- ジョブは全て冪等に設計し、at-least-once 配信を前提とする
- サーキットブレーカーで外部サービス（銀行API等）の障害を隔離する
