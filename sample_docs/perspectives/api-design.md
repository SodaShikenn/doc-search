# API設計観点

公開API・内部APIを設計するときの観点。

## リソース設計

- URLは名詞・複数形（/journal_entries）。動詞はHTTPメソッドで表現する
- 1リクエストの責務を1つに保つ。「ついでに」別リソースを更新しない
- レスポンスに内部実装の都合（DBのカラム名そのまま等）を漏らさない

## 冪等性とリトライ

- POST での作成系APIは Idempotency-Key ヘッダを受け付け、同一キーの再送では同じレスポンスを返す
- クライアントには指数バックオフ＋ジッターでのリトライを案内する
- タイムアウトしたリクエストが「実は成功していた」ケースを設計段階で考慮する

## バージョニングと互換性

- 破壊的変更（フィールド削除・型変更・必須化）は新バージョンでのみ行う
- 追加的変更（オプショナルなフィールド追加）は同一バージョンで可
- 廃止予定は Deprecation ヘッダとドキュメントで事前告知し、利用状況を計測してから削除する

## エラーレスポンス

- 構造化されたエラー形式（code, message, details[]）を全APIで統一する
- 4xx はクライアントが直せるもの、5xx はサーバー側の問題、と使い分ける
- バリデーションエラーはフィールド単位で返す（フォームにマッピングできるように）

## ページネーションとレート制限

- 一覧APIは必ずページネーションを付ける（上限なしの全件取得を作らない）
- カーソル方式を基本とし、total_count が必要な場合のみ別途提供
- レート制限は 429 + Retry-After で返し、上限をドキュメントに明記する
